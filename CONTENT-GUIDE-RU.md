## LinkedIn, личная почта и контакты лаборатории

В `src/data/members.json` найдите объект по `id` и заполните `linkedin` и `email`:

```json
"linkedin": "https://www.linkedin.com/in/EXACT-PROFILE-SLUG/",
"email": "person@example.org"
```

Это примеры, не настоящие контакты! Копируйте адрес LinkedIn непосредственно из профиля конкретного участника: по имени нельзя надежно определить нужного человека. Почта указывается без `mailto:` — сайт добавляет его сам. При `null` соответствующая кнопка скрыта. Проверка сборки принимает личные LinkedIn-ссылки `/in/` и проверяет формат почты, но не подтверждает владельца или существование ящика.

Общая почта: `lab.email` в `src/data/site.ts`; сейчас `datalab@sdu.edu.kz` (существующее значение, принадлежность не проверена). Там же название, адрес, описание. Общая почта используется и для заявок на вакансии.

Общие соцсети: в начале `src/data/site.ts` замените `.parse([])` на, например:

```ts
.parse([
  { label: "LinkedIn", url: "https://www.linkedin.com/company/EXACT-LAB-SLUG/" },
  { label: "GitHub", url: "https://github.com/EXACT-LAB-ACCOUNT" },
]);
```

Вставляйте только реальные подтвержденные адреса. Пустой список скрывает блок соцсетей.

## Общее hero-фото

Текущие файлы: `public/images/hero-team-1920.webp` (1920×1080) и `hero-team-960.webp` (960×540). Это две версии одного кадра; заменяйте обе одновременно. Браузер выбирает подходящий размер. На сайте ширина до 1124 px, на телефоне — ширина экрана минус 40 px; высота пропорциональна, обрезки нет.

Для простой замены используйте горизонтальный кадр 16:9 указанных размеров. Если пропорции другие, измените `width` и `height` в `src/components/sections/HomeSection.astro` на реальные размеры большой версии — это предотвращает скачок верстки при загрузке. Там же редактируются `alt` и подпись.

Существующий `scripts/prepare-hero-image.py` делает две WebP-версии из исходника, сохраняет пропорции и поворот EXIF. Он использует локальные Pillow/pillow-heif из `.tools`; после клонирования эти зависимости нужно установить отдельно. Если исходник не 16:9, обновите HTML-размеры, как описано выше.

## Новости

`src/data/news.json`: `category: "world"` для AI/ML, `"lab"` для лаборатории. У мировых новостей заполните `source: { "name": "Название источника", "url": "https://..." }`. Дата — дата публикации, не дата добавления. Раздел показывает новости по убыванию даты. Добавленная подборка проверена 16 сентября 2026; автоматического обновления нет. При следующем обновлении поменяйте дату проверки в `NewsSection.astro`.

## Проекты

`src/data/projects.json`. Пока список пуст, в разделе показывается заглушка со ссылкой на GitHub. Пример записи:

```json
{
  "id": "student-wellbeing-dashboard",
  "title": "Student wellbeing dashboard",
  "summary": "Одно-два предложения о том, что делает проект и зачем.",
  "status": "ongoing",
  "year": 2026,
  "tags": ["Sentiment analysis", "Streamlit"],
  "team": ["Имя Фамилия", "Имя Фамилия"],
  "repo": "https://github.com/SDU-Data-Analytics-Lab/...",
  "demo": null,
  "paper": null,
  "order": 1
}
```

`status`: `"ongoing"` или `"completed"`. `tags` — 3–4 коротких ключевых слова. Необязательны все поля, кроме `title`, `summary` и `order`. После переноса репозитория на GitHub лаборатории обновите `repo`. Порядок карточек задаёт `order`.

## Блог

Каждая статья — отдельный Markdown-файл в `src/content/blog/`. Имя файла становится адресом страницы: `aict2026-baku.md` → `/blog/aict2026-baku/`. В начале файла:

```yaml
---
title: "Заголовок"
date: 2026-10-12
excerpt: "1–2 предложения для карточки в разделе Blog"
cover:            # необязательно
  src: /images/blog/photo-1600.webp
  srcSmall: /images/blog/photo-800.webp
  width: 1600
  height: 1067
  alt: "Что на фото"
  credit: "Автор фото"              # для чужих фото обязательно
  creditUrl: "https://..."
  license: "CC BY 3.0"
  licenseUrl: "https://..."
---
```

Ниже обычный текст: абзацы, `## подзаголовки`, списки, ссылки. Если текста под шапкой нет, в разделе показывается только карточка без ссылки «Read post». Фото из интернета берите только со свободной лицензией (например, Wikimedia Commons) и указывайте автора в `credit`.

## Сборка и публикация

```sh
npm run build
npm run preview
```

После проверки: `npm run deploy`. Изменения локальных файлов сами по себе не обновляют опубликованный сайт.

## Безопасность: что есть и что настроить

Сайт статический: без базы данных, авторизации, загрузки файлов и серверного API. Это уменьшает поверхность атаки. В `public/_headers` уже есть CSP, HSTS, запрет встраивания в iframe, nosniff и ограничения браузерных разрешений. Ссылки проверяются при сборке, JSON-LD экранируется от закрытия тега script через контент.

Обнаруженные ограничения:

- Заголовки в файле не доказывают, что они включены на рабочем домене. После публикации проверьте ответ сервера в DevTools → Network → документ → Response Headers. Cloudflare применяет `_headers` к статическим ресурсам; для будущего Worker API заголовки нужно задавать отдельно.
- `npm run deploy` использует `wrangler@latest`: версия инструмента может измениться между публикациями. Для воспроизводимых выпусков закрепите проверенную версию Wrangler в devDependencies и lock-файле, затем используйте `wrangler deploy`.
- Шрифты загружаются с Google Fonts: есть сторонний запрос и зависимость от доступности сервиса. Для большей приватности можно хранить шрифты локально.
- Публичная почта может собираться спам-ботами. Используйте отдельный рабочий ящик с фильтрацией. `mailto:` открывает почтовый клиент и не отправляет письма с сервера сайта.
- `.gitignore` исключает ключи и `.env`, но не удаляет секреты из старой истории Git. Не кладите секреты в `public/`, JSON или клиентский код.

Простая схема: домен + Cloudflare Workers Static Assets + HTTPS + двухфакторная защита учетных записей регистратора, Cloudflare и Git. Сам домен защитой не является. Для Workers Custom Domain Cloudflare управляет сертификатом. Настройте редирект HTTP → HTTPS; включите DNSSEC там, где это поддерживается регистратором, и защиту от переноса домена. HSTS сейчас включает `includeSubDomains`: все поддомены должны поддерживать HTTPS.

Если позже появятся формы/API, потребуются серверная валидация, ограничения частоты запросов, защита от спама и хранение секретов только на сервере. Для нынешнего статического сайта добавлять собственную систему паролей не требуется.

Проверка `npm audit --omit=dev` 16.09.2026: 0 известных уязвимостей в проверенных production-зависимостях. Это не полный аудит безопасности; настройки аккаунтов и рабочего домена не проверялись.
